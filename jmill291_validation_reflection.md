# MiniProject3 Validation Reflection

The validation process showed that agreement was generally high, but some fields were much more subjective than others. HasRecovered and WhyRecovered had the strongest agreement because the presence of commits after an inactivity period was usually easy to identify from the timeline and gap commits. ActivityPattern required more interpretation because a project with bursts of development could appear cyclical at first, even when there was no predictable repeating pattern. During adjudication, several projects originally labeled cyclical were changed to irregular or declining after comparing activity across multiple years rather than focusing on isolated bursts.

Long gaps were often preceded by declining or increasingly sparse commit activity. Projects such as RItools, textreuse, and other maintenance-oriented repositories showed that development can gradually decrease before a long inactive period. However, a gap did not necessarily mean that a project was permanently dead. Recovery was often triggered by a specific maintenance need, compatibility problem, release, new feature, or contributor activity. For example, some projects resumed because dependencies or language versions needed updating, while others returned for bug fixes or release work. In other cases, only documentation or a small number of commits returned, showing that recovery can be limited rather than a complete return to sustained development.

The validation also showed that repository inactivity must be interpreted carefully. A long gap can represent abandonment, but it can also reflect a mature project that only requires occasional maintenance, a research artifact that is updated infrequently, or a project that becomes active again when a new technical need appears. FreeSurfer demonstrated another important case: because it never had a true zero-commit inactivity gap, labeling HasRecovered as either Yes or No was misleading. We resolved that disagreement by using N/A because there was no recovery event to evaluate.

The largest source of disagreement was RecentThemes. Small differences in commit selection or classification could change the two dominant themes. For NeuroElectro, my original classification included automated bot contributions, but review of the actual latest ten default-branch commits showed documentation and feature development instead. Similar disagreements occurred when dependency updates could also be interpreted as bug fixes, or when release commits competed with other categories. Using the same ten-commit window and applying the coding categories consistently made these decisions more reproducible.

Currentstatus also exposed an important data-quality issue. In the Falcor and textreuse cases, different data sources or dates produced different interpretations of whether a project was active. We resolved those disagreements by consistently using the assignment's cutoff window and the upstream default GitHub branch. This showed why qualitative validation needs clearly defined scope: two classifications can both appear reasonable when they are based on different branches, time periods, or data sources.

Overall, the adjudication process improved consistency by forcing us to explain each classification with evidence instead of relying only on an initial impression. The main recurring pitfalls were treating irregular bursts as cycles, using different repository scopes, interpreting similar maintenance commits differently, and assuming that any resumed activity represented a full recovery. Discussing these cases and applying the coding guide consistently resulted in agreement on all disagreements after discussion.
